1. Prerequisites and safety

These tests change real vault and external-service state. Use a test vault or a backed-up vault.

  • Android 8.0+ device (the reference device is an OPPO CPH2173, Android 14), CipherKeep 2.3.9 installed, autofill service set to CipherKeep.
  • Vault unlocked for the in-app sections. Travel Mode and recovery tests require the master password.
  • Notification permission allowed (Android 13+) if you want to see the “Save this login?” prompt.
  • For external features you need: a deployed Cloudflare Worker for emergency access, a deployed alias provider, an authenticator with the WebAuthn PRF extension, and a shared folder (Syncthing, USB, Drive, etc.).
  • Back up the vault before family join or key rotation: joining a family vault replaces the local vault identity on that device.
Never paste real recovery shares, member secrets or hardware credentials into a chat, a ticket or a screenshot. This guide only uses placeholders.

2. Autofill “save login” prompt new in 2.3.9

Goal: when you type a login by hand in an app or website that has no CipherKeep record, CipherKeep offers to store it without making you leave the app.

How it works

  • When an unlocked vault answers an autofill request, it also registers a save request with Android (username + password fields).
  • When the login form is submitted and the login screen is left or closed, Android sends the typed values to CipherKeep.
  • CipherKeep posts a notification: “Save this login to CipherKeep?” with Save and Not now. Nothing is stored unless you tap Save.
  • The new item gets a title from the app name (or the website domain), the username, the password and, for websites, the URL. It is stored in the background and appears at the top of the list because the default sort is “Recent”.

Test

  1. Make sure CipherKeep is unlocked and NOTIFICATION permission is allowed.
  2. Open an app or website login you have no saved record for. Tap the username field once (this lets Android ask CipherKeep for suggestions), then type a username and password manually.
  3. Submit the form (Log in / Continue / Sign in). Wait for the login screen to close or navigate away.
  4. Pull down the notification shade: “Save this login to CipherKeep?” should appear with the derived title.
  5. Tap Save. Open CipherKeep: a new record with that title, username and password is at the top of the vault list (sort “Recent”).
  6. Repeat with a second test and tap Not now: no record is created and the notification disappears.
Why a submission may not prompt: Android only reports a save when the app commits the form or finishes the login screen (typical after a successful login). A failed login that keeps the screen open does not produce a save request — this is an Android autofill rule, not a CipherKeep filter.
Notification permission denied: CipherKeep cannot ask; if the vault is unlocked it stores the login silently. Grant notifications to get the confirmation.
Duplicate protection: if an identical username + password already exists, no prompt is shown.

3. Folders, back navigation and Security tab 2.3.9

3.1 Open a folder’s contents

  1. Vault → tap Folders.
  2. Each folder row now has Open next to Rename/Delete. Tap Open (or tap the folder name).
  3. The dialog closes and the list is filtered to that folder (the filter field shows the folder name and the “N shown” counter drops).
  4. Clear the filter field to see all items again.

3.2 Return to the same list position

  1. Scroll down the vault list, or apply a search/filter/folder filter.
  2. Open a record, then press Back (phone or app button).
  3. Expected: you return to the same scroll position with the same search, filter, favourites toggle and sort order — not to the top and not to an unfiltered list.

3.3 Security tab

  1. Bottom navigation → Security.
  2. Expected: overview score card (score = 100 − at-risk items; counters Weak / Reused / Breached / No 2FA), Protection card, a plain-language “How CipherKeep protects you” card, and Breach monitoring.
  3. The duplicate “Password health” section is gone from this tab; password health remains under Settings.
  4. Settings → Advanced settings → Appearance: the “Design token gallery” button is gone. The old “Security” block (screenshots/backup/network) has moved to the Security tab as readable text.

4. Emergency access

Goal: if you become inactive, trusted contacts can recover the vault. A Cloudflare Worker (or compatible cron) holds one Shamir share; each contact holds another. Any two of the three shares reconstruct the vault key. The Worker never sees the vault key or plaintext.

What you need

  • The workers/emergency-cron Worker deployed with a KV namespace bound as POLICIES, and secrets EMERGENCY_TOKEN (32+ chars) and NOTIFY_TOKEN.
  • NOTIFY_WEBHOOK set to your email relay / ntfy endpoint (or empty for a dry run). The release payload contains each contact’s opaque share.
  • One or two contact email addresses you trust.

Fields

FieldMeaningExample
Cron HTTPS URLBase URL of the deployed Worker. HTTPS only, no credentials in the URL.https://emergency.example.workers.dev
Cron tokenShared secret equal to EMERGENCY_TOKEN. 32+ characters. Leave blank later to keep the saved token.stored in Keystore
Contact 1 emailFirst trusted contact. Receives one share at release time.alice@example.org
Contact 2 email (optional)Second trusted contact. With contact 1 they can already reconstruct; the cron share is a backup.bob@example.org
Inactivity daysDays without a check-in before the reminder/release timer starts.30
Grace minutesExtra window after the inactivity period before shares are released.60

Test (arm)

  1. Vault unlocked → Settings → Emergency access.
  2. Enter the Worker URL, token, contact emails, inactivity days and grace minutes.
  3. Tap Arm emergency access.
  4. Expected: a status line like Policy armed; release deadline <unix time> and a “Give these shares to the contacts offline” block listing contact-1: <share> and contact-2: <share>.
  5. Send each share to its contact through a different channel (in person, offline) and delete the message afterwards. The cron keeps the third share encrypted at rest in KV.
  6. Verify the policy from a terminal: curl -H "Authorization: Bearer $EMERGENCY_TOKEN" https://your-worker/policies/<id>. Expect state:"armed", your inactivity/grace values and a lastCheckIn timestamp.

Test (check-in and cancel)

  1. Tap Check in: the status deadline moves forward by the inactivity window. Do this regularly; the Worker sends one reminder and one release per policy.
  2. Tap Cancel: the policy becomes cancelled and never releases.

Test (recovering with shares)

  1. On the CipherKeep lock screen tap Forgot password? Use recovery shares.
  2. Paste any two of the three shares (the two contact shares, or one contact share plus the released cron share) and choose a new master password.
  3. Tap Recover. Expected: the vault unlocks with the new password; the shares are rotated and new shares are shown — distribute the new ones.
Limitations: coercion is not solved; a contact’s identity is verified only by the delivery channel; the released share alone is useless without a second share.

5. Travel Mode

Goal: hide the vault quickly when crossing a border or under pressure. The vault is not deleted; the app locks, the item list empties and autofill returns nothing until the master password is entered again.

Fields

FieldMeaning
Master password (on the Travel screen)Required to restore the vault. There is no separate Travel password.

Test

  1. Vault unlocked → Settings → Travel Mode → Enable Travel Mode.
  2. Expected: the app immediately locks and shows the Travel screen (“This vault is hidden…”). The vault list, search, autofill and the CipherKeep autofill suggestions are empty while Travel Mode is active.
  3. Open another app with a login form and tap a field: the CipherKeep suggestion list is empty (the service has no items).
  4. Return to CipherKeep, type the master password and tap Restore vault. Expected: the vault unlocks and items return.
  5. To keep the hidden state after a restart, leave Travel Mode enabled; do not restore until it is safe.
This is not plausible deniability: local app data still shows that a vault exists. Travel Mode hides contents from casual inspection and autofill, not from forensic analysis.

6. Family sharing

Goal: share one vault with approved members. The owner wraps the vault key to each member’s X25519 public key. Members unwrap it with their secret to join. Revoking a member rotates the vault key so future writes are not readable by them.

Roles and key material

  • Owner: creates the vault identity; fingerprint is shared out of band.
  • Editor: proposed role for members who may change items.
  • Viewer: proposed role for read-only members. The role is part of the envelope, so it must match at join time.
  • Vault id: the 32-hex sync namespace, shown to the owner and required by the member when joining.
  • Member id, public key (64 hex), secret (64 hex), fingerprint: created on the member device and shown in the “Member: create your identity” section.
  • Envelope: ephemeralPublic (64 hex), nonce (48 hex), ciphertext (hex). Generated by the owner when inviting and displayed next to the member.

Test A — create the family (owner device)

  1. Settings → Family sharing → Create family owner identity. Copy the owner fingerprint and verify it with members out of band.
  2. Copy the Vault id (32 hex) shown under the fingerprint; members need it.
  3. On the member device, in the same screen, scroll to Member: create your identity, enter a member id, choose Editor or Viewer, tap Create member identity.
  4. The member sees member id, public key, secret and fingerprint. Tap Copy public and send the member id + public key to the owner. Keep the secret on the member device.

Test B — invite (owner device)

  1. Paste the member id and public key, choose the same role, tap Invite member.
  2. Expected: the member appears with role and an envelope. Copy ephemeralPublic, nonce and ciphertext with the buttons and send them plus the vault id to the member (the secret must never be sent back to the owner).

Test C — join (member device)

  1. Fresh install or backed-up device. Settings → Family sharing → Join a family vault.
  2. Paste: vault id, your member id, the envelope ephemeral public (not your own public key), nonce, ciphertext, your member secret; type a new local master password; choose the same role.
  3. Tap Join family vault. Expected: “Joined family vault…”. The local vault now uses the family key; configure relay sync and download.

Test D — change role and revoke

  1. Owner: Make viewer / Make editor rewraps the key and updates the member’s envelope; send the new envelope to the member.
  2. Owner: Revoke → confirm “Revoke and rotate”. The vault key rotates and remaining members are rewrapped.
  3. Expected: the removed member cannot read new ciphertext; anything already downloaded stays readable. Audit entries record invited / role_changed / revoked.
Never join a family vault on your main device without a backup: joining replaces the local vault identity and sync namespace.

7. Email aliases

Goal: create per-site email aliases through a provider you control, store them in the vault, and disable or delete them without leaving CipherKeep. CipherKeep never proxies mail.

Supported providers

ProviderBase URLTokenEndpoints used
Cloudflare (self-hosted Worker)Your Worker HTTPS URL32+ charsPOST/GET /aliases, POST /aliases/{address}/disable, POST /aliases/{address}/delete
SimpleLogin (self-hosted)Your SimpleLogin HTTPS URL20+ charsGET /api/aliases, POST /api/alias/create, POST /api/alias/toggle/{id}, DELETE /api/alias/{id}

Fields

FieldMeaning
Provider buttonsCloudflare or SimpleLogin. Determines the API shape.
Provider HTTPS URLBase URL, HTTPS only, no user:password in the URL.
Provider tokenAPI token, saved in Keystore-backed storage. Blank keeps the saved token.
Site name for new aliasLabel used to build the alias prefix/note (1–128 chars).

Test

  1. Settings → Email aliases, choose the provider, enter URL and token → Save provider. Expected: “Provider saved” and the existing alias list loads.
  2. Enter a site name → Create alias. Expected: the provider creates the alias, CipherKeep stores it as a vault item, and it appears in the list with provider/label/enabled state.
  3. Copy copies the address and clears the clipboard after 30 seconds.
  4. Disable toggles the alias off at the provider and updates the stored item; Delete removes it at the provider and from the vault.
  5. Check the provider dashboard: the alias exists, is disabled, or is gone as expected.
The provider must be reachable over HTTPS and accept the token; errors are shown as “Provider configuration rejected”, “Provider list failed”, “Alias creation failed”, “Disable failed” or “Delete failed”.

8. Hardware unlock (WebAuthn PRF)

Goal: unlock the vault with a hardware authenticator that supports the WebAuthn PRF extension. A PRF output wraps the vault key; the password and recovery shares remain fallbacks.

What you need

  • Android 14+ with Credential Manager; a security key or platform authenticator that supports WebAuthn PRF (for example a FIDO2 key with the PRF extension).
  • Vault unlocked and the authenticator available.

Test (enroll)

  1. Settings → Advanced settings → Hardware unlock (WebAuthn PRF).
  2. Tap Enroll security key; approve creation with the authenticator (PIN/biometric as requested).
  3. Expected: “Enrolled. Password and recovery shares remain valid.” If the authenticator returns PRF only on assertions, CipherKeep performs the first assertion automatically; otherwise you get “Unsupported authenticator, cancelled, or no PRF result.”

Test (unlock and remove)

  1. Lock the vault, tap Unlock at the hardware section, and approve the assertion. Expected: “Unlocked with the security key.”
  2. Tap Remove: the record is deleted and password unlock remains.
The enrollment record (credential id, salt, sealed vault key) is stored in Keystore-backed storage. The PRF output is never stored; it is zeroed after use. Unsupported authenticators cannot enroll, and the feature never weakens password/recovery access.

9. Local-folder sync

Goal: sync between devices through a folder you control (Syncthing, USB, cloud drive) without any relay. Only sealed manifests and opaque blobs are written.

Fields and controls

ControlMeaning
Choose/Change sync folderAndroid SAF folder picker; the app keeps persistable read/write permission.
Verify folder accessCreates and deletes a probe file; expected “Folder write/delete verified.”
Sync folderMerges local records with the folder manifest and writes the sealed manifest + blobs. Expected “Synced N record(s); conflicts M.”
Folder: URIShows the selected folder; “No folder selected” means sync stays offline.

Test (two devices)

  1. On device A: Settings → Advanced settings → Local-folder sync → Choose sync folder, pick a folder (for example Download/CipherKeepSync).
  2. Tap Verify folder access; expect the verified message.
  3. On device B: choose the same shared folder (via Syncthing/USB/Drive) and verify access.
  4. On A: Sync folder; expect “Synced N record(s)”. Files manifest-* appear in the folder.
  5. On B: Sync folder; the records appear. Add an item on B, sync, then sync on A: the item propagates. Deletions propagate as tombstones.
  6. Inspect the folder: manifests and blobs are ciphertext; no plaintext item names or passwords.
Treat the folder as a transport, not a backup: the manifest is sealed to the vault. Use one writer at a time; conflicts are reported and can be resolved as in relay sync.

10. Troubleshooting and diagnostics

Autofill

  • Check the system autofill service is CipherKeep: Settings → System → Languages & input → Autofill.
  • Watch logs: adb logcat -s CipherKeepAutofill CipherKeepAutofillFields. Each request logs package, domain, field flags, match count and dataset count. No values or secrets are logged.
  • Locked vault: the popup shows Unlock CipherKeep; the sheet returns to the app after unlock.
  • Notification prompts: allow notifications (Android 13+). Without it CipherKeep stores silently when unlocked.

Emergency / aliases / folder sync

  • All remote calls require HTTPS, reject credentials in URLs, use 15–20 s timeouts and bounded response sizes.
  • HTTP failures are generic in the UI by design; use the Worker/provider logs to see the status code.

Family

  • “Join failed”: verify the ephemeral public (from the envelope, not your own public key), the nonce, the ciphertext, the role and the secret.
  • “Invite failed”: the public key must be exactly 64 hex characters.
  • Revocation rotates the key; download the new envelope from the owner afterwards.

Useful Android commands

adb shell dumpsys autofill | grep -i cipherkeep
adb shell dumpsys notification --noredact | grep -i cipherkeep
adb logcat -s CipherKeepSync CipherKeepBiometric CipherKeepAutofill
